# gogmeet-performance-enhancement - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** A safer, less wasteful calendar pipeline: disabled auto-open will no longer break countdowns or churn timers, oversized macOS helper output will fail predictably without pointless recompilation, Google authentication and network failures will preserve usable credentials, and stale or incomplete calendar data will never drive automatic meeting actions. The repository will also gain trustworthy, privacy-safe measurement tools for deciding which remaining performance candidates are worth a separate implementation plan.

**Why this approach:** Correctness and resource bounds come first because those failures are proven by code and execution. The remaining speed ideas are intentionally measurement-only: no optimization is promoted from source inspection or a noisy microbenchmark.

**What it will NOT do:** It will not add Google incremental synchronization, weaken encryption or Electron security, use an unbounded process buffer, auto-connect OAuth at startup, or silently ship renderer, tray, alert-window, startup, or packaging changes without native evidence.

**Effort:** Large
**Risk:** High - calendar result semantics, scheduling ownership, OAuth persistence, IPC, and cross-platform process behavior all change, although each change is isolated behind TDD and explicit security guardrails.
**Decisions to sanity-check:** Degraded data remains visible and explicitly joinable but cannot automate; process and HTTP byte/time ceilings are engineering safety limits, not claimed optima; measurement candidates produce receipts and follow-up recommendations rather than speculative product changes.

## Scope
### Must have

- Correct scheduler snapshot, countdown, alert-timer idempotence, and sleep-blocker balance when `autoOpenEnabled=false` without creating browser-open actions.
- Replace buffered Swift helper execution with a dedicated bounded streaming runner. Initial safety constants are `8 MiB` stdout, `256 KiB` stderr, and `15 s` execution timeout; these are explicit allocation/diagnostic ceilings, not performance optima, and are tested at `limit - 1`, `limit`, and `limit + 1`.
- Recompile the helper at most once and only for executable-integrity failures (`ENOENT`, `ENOEXEC`, or verified cache/hash mismatch), never for timeout, output limit, semantic EventKit exit, malformed payload, or parser failure.
- Centralize Google HTTP with a `15 s` per-request headers+body deadline, `8 MiB` response-body ceiling, and `60 s` overall poll budget. These are initial safety limits below the shortest `120 s` poll cadence, not claimed optimal values.
- Force one real Google token refresh after API 401; preserve encrypted credentials for timeout, network, abort, 429, 5xx, malformed response, configuration errors, and temporary secure-storage unavailability.
- Define exhaustive successful-result provenance: live complete, live partial, or offline cache, with observation/cache timestamps. No optional metadata may require caller guesswork.
- Treat partial/offline events as display and explicit-join data only. Degraded publication cancels pending automatic browser, alert, notification, title/countdown, and late-auto-join work while preserving popover, tray, and global-shortcut joins through `graph.join.byId` and existing egress allowlisting.
- Store only complete live Google snapshots in a versioned encrypted cache. Reject corrupt, unversioned, unknown-version, non-finite, or materially future-dated metadata; filter ended cached events; never use cache age to enable automation.
- Route startup, watcher, permission, settings, visibility, manual, shortcut-fallback, and join-fallback refreshes through one main-process coordinator with one in-flight provider call, one latest queued follow-up, monotonic publication generation, and latest-eligible-result wins.
- Repair the parser benchmark to use valid production nine-string JSON Lines and add opt-in, redacted measurement infrastructure with correctness preflight and machine metadata.
- Run six conditional experiments for Google fields/polling, tray rebuilds, `safeStorage`, startup/helper launch, alert lifecycle, and build/package behavior. Each ends as `retained`, `rejected`, `blocked`, or `skipped`; this plan does not implement their product optimizations.

### Must NOT have (guardrails, anti-slop, scope boundaries)

- No Google `syncToken`, webhook/push service, durable event database, recurrence redesign, or calendar-account migration.
- No unbounded child-process or HTTP-body buffering and no change that merely increases `execFile.maxBuffer`.
- No plaintext token/cache fallback, longer-lived plaintext caching, disabled `safeStorage`, or credential deletion for transient failures.
- No automatic browser, alert, notification, title/countdown, late-join, or other scheduler action from partial/offline results.
- No removal of explicit user joins from degraded data; all joins must retain `joinMeetingById`/allowlisted egress.
- No provider-only shared Promise presented as complete refresh coordination; no stale completion publication.
- No raw IPC, sender-validation weakening, compatibility shim, deprecated channel, sandbox/context-isolation change, Node integration, PKCE/state weakening, embedded OAuth, or broader URL egress.
- No secrets or user calendar content in traces: tokens, authorization headers, emails, calendar IDs, event titles/descriptions, meeting URLs, PKCE state/verifier, raw bodies, or decrypted payloads.
- No default-on tracing, uncalibrated benchmark CI gate, locale-pruning task, renderer framework migration, dependency upgrade, broad refactor, or unrelated cleanup.
- No prebuilt Swift helper distribution in this plan; it requires a separate signing, notarization, entitlement, TCC, x64, and arm64 plan after cold-start evidence.

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: TDD for every mandatory behavior change using the existing Vitest workspace; tests-first correctness preflight plus read-only/native measurement for conditional experiments.
- Focused commands use the configured projects, for example `bunx vitest run -c vitest.workspace.ts --project main tests/main/<file>.test.ts`, `--project application`, and `--project renderer`. Do not use direct `bun test` as a substitute for workspace execution.
- Repository-wide gates: `bun run validate:node`, `bun run format:check`, `bun run typecheck`, `bun run lint`, `bun run test`, `bun run test:coverage`, and `bun run build`.
- Native/package gates use repository commands only where the host supports them: `bun run package:mac`, `bun run package:win:x64`, `bun run package:win:arm64`, `bun run merge:windows-latest-yml`, `bun run verify:macos-release`, and `bun run verify:windows-release`.
- Evidence: `.omo/evidence/gogmeet-performance/task-<N>-<slug>/...`. If execution runs under `ulw-loop`, use its `currentAttemptDir` instead and record that path in the task receipt.
- Conditional native/API receipt format: task ID; `retained|rejected|blocked|skipped`; host OS/architecture; exact prerequisite probe/command; exit code and redacted output summary; deterministic substitute run; residual unverified claim; confirmation that no product optimization was retained.
- Fixed benchmark protocol is an engineering repeatability decision, not a performance optimum: fixture generation outside timed regions; 5 warmups and 30 measured iterations for local microbenchmarks; p50/p95/min/max/sample count; 3 warmups and 10 paired polls for authenticated Google shadow tests; 10 cold launches per native platform; 5 clean builds; 3 native packages per target. A receipt must state when variance invalidates a comparison.
- Any measurement instrumentation added to product paths is opt-in with `GOGMEET_PERF_TRACE=1`, redacted by automated tests, and removed after measurement unless Task 9 explicitly retains the generic trace primitive.
