# gogmeet-performance-stability-hardening - Work Plan

## TL;DR (For humans)
**What you'll get:** Missing Google events can no longer be silently treated as a complete calendar, rate limiting will not trigger an immediate second request, alert windows cannot reappear or mutate after replacement/shutdown, and the long-running calendar watcher cannot grow memory or logs without bounds. The performance lab will also collect real packaged startup, tray, alert, and Windows encrypted-storage evidence instead of relying on synthetic stand-ins.

**Why this approach:** Deterministic correctness and stability defects are fixed before measurement work. Performance conclusions remain gated on repeatable native evidence from the actual packaged paths, with strict privacy, architecture, variance, and cleanup checks.

**What it will NOT do:** It will not ship a performance optimization, weaken security or encryption, change release packaging, add public settings or services, access real calendar data in probes, or treat a cross-built/blocked/synthetic run as native success.

**Effort:** XL
**Risk:** High - the work crosses calendar consistency, Electron lifecycle, child-process bounds, encrypted persistence, native packaging, and cross-platform CI.
**Decisions to sanity-check:** Preserve the 50-page ceiling while classifying exhaustion; use 8 MiB/256 KiB watcher limits; cap traces at 1,024 rows and 1 MiB; keep all measurement outcomes advisory until a separate plan is approved.

Your next move: start implementation in a worker session or request the optional dual high-accuracy plan review. Full execution detail follows below.

## Scope
### Must have
- Explicit Google pagination exhaustion outcomes for calendar-list, full-event, and incremental-event traversals; incomplete data cannot be reported as live complete or mutate incomplete per-calendar state.
- Generation-safe alert queue handoff, reuse, presentation, and teardown, including cancellation of the module-owned queued immediate.
- Distinct Google rate-limit handling that prevents incremental 429 from issuing a same-poll full-window request while preserving 410 and 5xx behavior.
- Fixed Darwin watch-sidecar stdout/stderr ceilings with deterministic overflow, suppression, restart, and teardown behavior.
- A bounded, redacted, opt-in trace buffer and fixed-file atomic flush under isolated Electron `userData`, with finite startup phase identities.
- A private packaged measurement mode with isolated `userData`, deterministic readiness/timeout/teardown, synthetic-only fixtures, and truthful host/artifact architecture metadata.
- Faithful packaged startup, tray, alert, and native Windows token/offline-cache measurements, with documented thresholds and terminal receipts.
- Non-PR-blocking native measurement CI jobs, updated lab documentation, permanent bound/freeze checks, and full regression verification.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- No product optimization based on this plan. A `retained` receipt authorizes only a separate user-approved plan and must retain `productChange: "none"`.
- No increase/removal of `MAX_PAGES`, Google HTTP/body/poll limits, one-shot Swift limits, or kill deadlines. New sidecar limits match the frozen one-shot byte values without modifying those constants.
- No cache or sync-token commit from an incomplete calendar traversal; no loss of existing index/token on full or incremental exhaustion.
- No retry loop, forced OAuth refresh, credential deletion, raw response logging, or sync-token clearing for HTTP 429.
- No alert queue cap/expiry feature, destroy/recreate product rollback, renderer contract change, user-dismiss semantic change, or weakened `SECURE_WEB_PREFERENCES`.
- No plaintext token/cache fallback, default-userData probe writes, user calendar/network access in packaged probe mode, or secret/user-content fields in traces and receipts.
- No caller-controlled product trace path, arbitrary metadata bag, unbounded trace rows/bytes, non-atomic flush, or evidence stored inside disposable probe `userData`.
- No public setting, new IPC channel, dependency upgrade, schema migration, webhook/push service, durable event database, lifecycle reorder, auto-OAuth, updater-delay change, or release packaging change.
- No native success claim from a cross-built artifact. Host and artifact architecture must match and the packaged process must actually run.
- No commits, branch operations, push, or PR unless the user separately authorizes them during execution.

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: **TDD with Vitest** for every product or config-with-logic change. Add the focused test first, run it against unchanged production code, and retain the assertion-level RED receipt; make the smallest production change; rerun for GREEN. Existing behavior tests are characterization coverage and must remain green.
- Evidence root: `<attemptDir>` is `currentAttemptDir` from `omo ulw-loop status --json`; outside ulw-loop use `.omo/evidence/gogmeet-performance-stability-hardening/`. Every todo writes `<attemptDir>/task-<N>-<slug>/red.txt`, `green.txt`, `qa.json|md`, and `cleanup.txt`.
- RED validity: the failure must cite the newly added assertion or missing behavior, not compilation, fixture, or environment failure. If the pre-change test unexpectedly passes, stop and refine the test before editing production code.
- GREEN validity: run the focused command named by the todo, then adjacent regression suites. Never delete/weaken tests, add `.only`/`.skip`, or suppress type errors.
- Real surface: deterministic product fixes use their actual provider/BrowserWindow/child-process seam with controlled mocks plus the packaged app where applicable. Measurement work must launch the packaged Electron process; plain Node imports of Electron and synthetic array work are not surface proof.
- Native status: missing runner/package/credential may produce a truthful `blocked` receipt only where the todo explicitly permits it. Probe crash, timeout, malformed trace, secret leak, failed cleanup, architecture mismatch, or behavior failure exits nonzero and is not `blocked` success.
- Teardown: every spawned process, temporary directory, packaged window/tray, timer, listener, and evidence writer has an explicit cleanup assertion. A leftover resource fails QA.
- Repository gates after implementation: `bun run typecheck`, `bun run lint`, `bun run format:check`, `bun run guardrails`, `bun run guardrails:tests`, `bun run test`, `bun run test:coverage`, and `bun run build` all exit `0` except documented unrelated pre-existing failures, which must be isolated before work starts.
